## 核心程序接口

拟定三个公共操作，均围绕已经绑定数据根目录的 `VistaStore` 对象执行。

```python
store = VistaStore(root)

summary = store.save_record(
    png=png_bytes,
    label="第 1 次渲染",
    glsl=glsl_text,
    source_agent="generation",
    render={"time": 0, "uniforms": {"radius": 0.2}},
)

catalog = store.list_records()
result = store.read_record(summary["record"], content="both")
```

### 根目录绑定

`VistaStore(root)` 接收路径字符串或 `Path`，将其解析为固定的绝对路径，并准备 `png/`、`glsl/`、`json/` 三个子目录。目录不可用时立即报告错误。

模型工具的参数只包含记录文件名和读取模式。记录与内容路径均在绑定根目录内解析，并检查符号链接解析后的实际位置。

### 保存

```python
save_record(
    *,
    png: bytes,
    label: str,
    glsl: str | None = None,
    reuse_glsl_from: str | None = None,
    source_agent: str | None = None,
    render: dict | None = None,
) -> dict
```

| 参数 | 语义 |
| --- | --- |
| `png` | 本次实际 PNG 字节；持有文件路径的调用方先读取字节 |
| `label` | 调用方提供的记录名称 |
| `glsl` | 本次完整代码正文，按 UTF-8 原样保存 |
| `reuse_glsl_from` | 同库已有 JSON 文件名，复用该记录关联的稳定 GLSL |
| `source_agent` | 来源名称或 `None` |
| `render` | 实际外部参数对象，值采用标准 JSON 支持的类型 |

`glsl` 与 `reuse_glsl_from` 互斥，两者都省略时保存 `glsl: null`。复用来源必须存在且关联可读取的 GLSL。相同代码的复用由调用方显式指定，代码变化时提供新的正文。

核心验证输入 PNG 的格式与可解码性，保存原始字节。`render` 在写入前完成 JSON 序列化快照，拒绝非 JSON 类型、非字符串对象键和非有限数值。调用方负责参数的实际值及完整性。

`render=None` 时省略字段，传入空对象时保留空对象。记录只新增设计已经规定的字段，现有设计中的 JSON 示例可以直接读取。

成功结果使用统一摘要。

```json
{
  "record": "record-<unique>.json",
  "label": "第 1 次渲染",
  "source_agent": "generation",
  "has_glsl": true
}
```

`record-<unique>.json` 表示核心生成的唯一文件名。程序返回摘要后，调用方即可把它放入业务工具反馈。

每次成功保存采用追加语义，包括调用方重新发起的保存。调用方拿到摘要后，可以直接使用该记录；进程中断后可以通过目录扫描发现已发布记录。

### 列出与读取

`list_records()` 扫描 `json/` 中已发布的 JSON，按文件名字典序返回 `{"records": [...]}`。排序仅用于确定输出顺序。每条摘要由 `record`、`label`、`source_agent` 和 `has_glsl` 组成，`has_glsl` 根据 JSON 中的 `glsl` 是否为空计算。

`read_record(record, content="image")` 返回核心自己的 `RecordContent` 数据对象。

| 字段 | 内容 |
| --- | --- |
| `metadata` | `record`、`label`、`source_agent`，以及存在时的 `render` |
| `image` | 请求图片时的 PNG 字节，其余情况为 `None` |
| `code` | 请求代码且存在关联时的完整 GLSL，其余情况为 `None` |

读取模式沿用 `image`、`code`、`both`。`image` 读取 PNG，`code` 读取 GLSL，`both` 读取两者。每种模式都先验证 JSON 结构及路径归属，再访问请求的内容文件。

`glsl: null` 时，代码结果为 `None`；请求 `both` 仍返回图片。已登记的 GLSL 为空字符串时，结果保留空字符串。所请求的任一已登记文件丢失或损坏时，本次读取报告失败。

## 文件发布与错误处理

文件名由核心生成，PNG 和新 GLSL 使用独立唯一名称。复用 GLSL 时引用已有记录中的相对路径。

一次保存按以下顺序执行。

1. 验证输入、序列化元数据，确认复用来源可读。
2. 在相应子目录创建临时文件，写完并关闭 PNG 和新增 GLSL。
3. 原子发布内容文件，检测目标重名，保证已有文件内容稳定。
4. 完整写入 JSON 临时文件，最后原子发布正式 `.json` 文件。
5. 返回记录摘要。

首选实现为同目录临时文件、文件同步和 `os.link` 发布，利用目标已存在时失败的语义防止覆盖。临时文件采用 `.tmp` 后缀，目录扫描只发现正式 `.json`。测试覆盖并发保存和名称冲突。首轮验证使用本地文件系统；实现遇到不支持原子发布操作的文件系统时明确报错。

发布 JSON 是登记完成的时点。在此之前失败，尽力清理本次创建的独有文件并报告错误。复用的 GLSL 保持稳定。JSON 发布后，临时文件清理独立处理；清理失败时记录错误，仍返回成功摘要，已发布记录及内容继续保留。

进程崩溃可能留下临时文件或未登记的内容文件，目录扫描以正式 JSON 为准。崩溃发生在 JSON 发布之后、返回摘要之前时，下次扫描可以发现该记录。

| 情况 | 处理方式 |
| --- | --- |
| 空目录 | 返回空记录列表 |
| 扫描发现损坏 JSON | 整次列出失败，指出具体记录与原因 |
| JSON 结构或字段类型错误 | 返回明确的记录错误 |
| 记录文件名包含路径或越界引用 | 拒绝请求 |
| 文件或子目录的符号链接指向根目录外 | 拒绝访问 |
| `glsl: null` 且请求代码 | 正常返回无关联代码状态 |
| 已登记文件缺失、不可读或损坏 | 本次读取失败，指出所请求记录与文件 |
| 只请求图片且关联代码缺失 | 图片可以正常读取 |
| 只请求代码且关联图片缺失 | 代码可以正常读取 |
| JSON 发布前的写入、同步或发布失败 | 报告保存失败，尽力清理本次独有文件 |
| JSON 发布后的临时文件清理失败 | 记录清理错误，返回成功摘要并保留已发布记录 |

核心对外使用 `VistaError` 表达存储、记录及输入错误，并保留原始异常作为排查依据。目录列出检查 JSON 和路径，实体文件的可读性在请求对应内容时检查。

## MCP 接口与启动

适配层提供 `create_server(root)`，使用一个绑定该根目录的核心对象注册工具。CLI 提供显式的 `--root` 参数，通过 stdio 启动。

拟定安装和启动命令如下。

```bash
uv sync --extra mcp --group dev
uv run --extra mcp vista-memory-mcp --root /absolute/path/to/vista
```

标准输出承载协议消息，日志写入标准错误。CLI 参数错误和目录初始化错误使启动明确失败。两个工具的调用合同如下。

| 工具 | 输入 | 返回 |
| --- | --- | --- |
| `list_records()` | 空参数对象 | 包含目录 JSON 的文本内容 |
| `read_record(record, content="image")` | JSON 文件名与三选一读取模式 | 元数据文本，以及按需返回的图片、代码文本 |

`read_record()` 先输出一段 JSON 元数据文本。请求代码时，追加一段完整 GLSL 文本或“没有关联代码”。请求图片时，追加 MIME 类型为 `image/png` 的图像内容块。MCP 层负责将核心返回的 PNG 字节转换为协议图像内容。[官方图像内容说明](https://py.sdk.modelcontextprotocol.io/servers/media/)

核心读取失败映射为 MCP 工具错误，并提供可理解的错误文本。协议测试同时检查工具数量、参数 schema、默认读取模式和无效参数处理。

### 核心行为测试

测试使用临时数据根目录，覆盖以下行为。

- 参考图保存、列出、回读；空目录与无关联代码的正常结果。
- 共享同一 GLSL 的两条记录，各自保存并返回不同 PNG 和外部参数。
- 代码变化后写入新版本，旧记录继续返回原代码。
- 默认 `image` 及 `code`、`both` 三种模式的内容范围和元数据。
- 直接载入设计中的手写 JSON，确认既有字段格式可读。
- PNG 字节、GLSL 正文和嵌套参数的准确回读，调用方修改参数对象后的记录稳定性。
- 非法输入、损坏 JSON、缺失文件、越界路径及越界符号链接的明确错误。
- 文件写入和发布失败、重名冲突及多进程并发保存，确认已有记录与共享代码稳定。
- 在内容写完但 JSON 尚未发布时扫描目录，确认只有已完成记录可见。
- 新建核心对象读取同一数据目录，确认持久回读。

### MCP 协议测试

使用官方 SDK 客户端启动实际 CLI 子进程，完成握手并调用两个工具。对每次读取结果检查内容块类型、元数据和错误状态；将图像内容解码后与保存的 PNG 字节比较，同时核对 GLSL 正文。

服务运行期间由程序接口追加记录，再调用 `list_records()` 和 `read_record()`，确认服务能够发现新增记录。关闭客户端与服务后启动全新连接，验证旧记录仍可发现和读取。

### 本地连续记录示例

`examples/local_roundtrip.py` 按预设参数确定性生成不同 PNG，并立即登记三条记录；前两条共享 GLSL，分别携带不同 PNG 和参数，第三条使用新的 GLSL 正文。另外登记一张参考图。GLSL 使用固定的存取测试正文，每条夹具预先定义期望的图片字节、代码正文和参数值。

脚本通过核心接口登记，随后通过 MCP 协议发现并读取记录，逐字节核对图片与代码并比较参数；最后启动新连接回读旧记录。示例结果用于证明登记与传输的数据对应关系。Shader 执行和渲染效果在后续业务接入阶段验证。

拟定检查入口如下，实施后在 README 中给出可直接执行的最终命令。

```bash
uv run pytest tests/test_core.py
uv run --extra mcp pytest tests/test_mcp.py
uv run --extra mcp python examples/local_roundtrip.py --root /tmp/vista-example
uv run ruff check .
uv run ruff format --check .
uv build
```

构建后在仅安装核心依赖的临时环境检查核心导入与存取，再在安装 `mcp` 额外依赖的环境检查发布包的 CLI。示例重复执行时向指定目录追加新记录。
